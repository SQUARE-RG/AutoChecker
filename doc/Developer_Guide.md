# AutoChecker 开发者指南

感谢你关注 AutoChecker。本文面向希望修复问题、改进现有生成后端，或为项目增加新静态分析工具和编程语言支持的开发者。

AutoChecker 的目标不是维护一组固定检查规则，而是把编码规范、测试用例、漏洞及修复补丁转化为可执行的静态代码检查器。贡献代码时，请同时关注检查器能否生成、能否在真实工具链中执行，以及检测结果是否符合测试预期。

## 可以贡献什么

我们欢迎以下类型的贡献：

- 修复检查器生成、编译验证、测试执行和反馈修复过程中的问题；
- 改进提示词、知识检索、检测逻辑分解和迭代修复策略；
- 为 PMD、Clang-Tidy、CodeQL、Semgrep 等现有后端补充语言、规则类型或测试；
- 完善 Clang Static Analyzer 等实验性后端的工程化接口；
- 接入新的静态分析工具或新的编程语言；
- 为漏洞与补丁驱动路线补充漏洞分析、CodeQL 查询生成或差分谓词探测能力；
- 改进规范文档解析、规则抽取和测试用例生成；
- 补充安装文档、示例规则、可复现数据及使用说明。

如果改动范围较大，建议先创建 Issue，说明使用场景、输入输出、目标分析工具及预期验证方式，便于在实现前对接口和技术路线达成一致。

## 项目结构

以下目录与扩展开发最相关：

| 路径 | 作用 |
| --- | --- |
| `src/input_processing/` | 规范文档解析、规则抽取和测试用例生成 |
| `src/entity/` | 规则、测试用例和检查器等核心实体，以及分析器工厂 |
| `src/prompt/` | Clang-Tidy、CodeQL 等后端的生成提示词 |
| `src/retriever/` | 静态分析 API、文档、基础操作和示例的知识检索 |
| `src/plateform/` | 目标工具的编译、执行和验证适配层；目录名为项目现有命名 |
| `src/generator*.py` | 规范与测试用例驱动路线的检查器生成与迭代修复逻辑 |
| `src/main.py` | Clang-Tidy 等现有流程的命令行入口 |
| `src/main_codeql_uniform.py`、`src/codeql_agent/` | CodeQL C/C++、Python 规范驱动生成入口与智能体实现 |
| `src/main_semgrep.py`、`src/semgrep_generator.py` | Semgrep 规则生成与验证 |
| `tool/`、`framework/pmd_project/` | PMD 检查器生成实现及用于验证的 PMD 工程 |
| `src/autoql/` | 漏洞与补丁驱动的漏洞分析、CodeQL 查询生成、双版本验证和差分谓词探测 |
| `src/unit_test/`、`src/autoql/tests/` | 通用模块及漏洞与补丁驱动路线的测试 |
| `doc/` | 安装、部署、设计和开发文档 |

项目目前包含若干处于演进过程中的入口。修改代码前，请先确定改动属于“规范与测试用例驱动”还是“漏洞与补丁驱动”路线，并尽量沿用对应路线已有的数据结构、输出目录和验证流程，避免引入功能重复的新入口。

## 准备开发环境

推荐使用 Ubuntu 22.04、Python 3.10，并至少准备 16 GB 内存和 64 GB 可用磁盘空间。首先安装 Python 依赖：

```bash
git clone https://github.com/SQUARE-RG/AutoChecker.git
cd AutoChecker
conda create -n autochecker python=3.10
conda activate autochecker
pip install -r requirements.txt
```

根据准备开发的后端安装相应工具链：

- [PMD 部署说明](pmd_install_cn.md)
- [Clang-Tidy 部署说明](clang_tidy_install_cn.md)
- [CodeQL 部署说明](codeql_deploy_cn.md)
- [Semgrep 部署说明](semgrep_deploy_cn.md)

大模型密钥、模型名称和服务地址应通过项目配置或环境文件提供。不要把 API Key、访问令牌、私有仓库地址或包含敏感信息的运行日志提交到仓库。

## 开发流程

1. 从最新的主分支创建功能分支，分支名建议使用 `feature/<name>`、`fix/<name>` 或 `docs/<name>`。
2. 用一个最小规则或漏洞案例复现问题，并记录预期结果。
3. 将改动限制在对应模块；如需调整公共数据结构，应同步检查所有生成后端。
4. 为新行为增加单元测试或最小端到端测试，并使用真实分析器验证生成结果。
5. 更新受影响的 README、部署文档、配置示例和命令示例。
6. 提交 Pull Request，并在说明中列出改动动机、验证环境、执行命令和结果。

建议保持提交粒度清晰，不要在同一个提交中混入无关的格式化、数据文件或大规模重命名。

## 扩展新的静态分析工具

不同静态分析工具的检查器形式差异较大，因此新后端至少需要形成以下闭环：

```text
规则与测试用例
      ↓
检测逻辑与框架知识
      ↓
候选检查器生成
      ↓
编译或语法验证
      ↓
测试用例执行与结果解析
      ↓
反馈修复和最终检查器
```

实现时建议依次完成：

1. **定义能力边界**：说明目标工具、支持语言、检查器格式、适用生成路线以及暂不支持的检测能力。
2. **定义实体与输入映射**：复用或扩展 `src/entity/` 中的 Rule、Case 和 Checker 抽象，明确规则描述、测试路径和预期告警如何进入后端。
3. **实现工具适配层**：在 `src/plateform/` 中封装编译或语法检查、检查器执行、超时处理、退出码和诊断信息解析。不要把工具调用散落在提示词或业务逻辑中。
4. **实现生成与知识支持**：为目标工具增加提示词、查询模板、API 文档或示例知识，并在生成器中接入。检索数据应注明来源、版本和构建方式。
5. **实现结果判定**：将工具输出归一化为测试用例级结果，能够区分编译失败、违规用例漏报和合规用例误报。
6. **接入反馈修复**：向生成过程提供结构化诊断信息，并设置明确的迭代次数、超时和失败状态。
7. **提供入口与文档**：增加稳定的命令行入口、最小配置示例、安装说明和输出目录说明。
8. **补充测试**：至少提供一条应报告的违规用例和一条不应报告的合规用例，并覆盖一次完整的生成或验证过程。

如果新工具的执行模型与现有抽象差异明显，可以实现独立入口，但应保持统一的规则字段、结果字段和失败状态，并在开发者文档中说明差异。

## 扩展 CodeQL 语言支持

规范与测试用例驱动的 CodeQL 多语言差异集中在 `src/codeql_language_config.py`。新增语言时通常需要：

1. 增加对应的 `LanguageConfig`，配置源码扩展名、CodeQL language flag、数据库构建命令、QL pack 依赖和 import 语句；
2. 在 `get_language_config()` 中注册语言；
3. 增加该语言的查询模板或提示词；
4. 构建相应的 CodeQL 文档、标准库和本地查询知识集合；
5. 准备合规、违规测试用例，并验证数据库创建、查询编译和查询执行；
6. 更新 README 中的支持矩阵和 CodeQL 部署说明。

漏洞与补丁驱动路线当前主要位于 `src/autoql/`。扩展其语言支持时，还需要适配 CodeQL pack、漏洞与修复数据库、源码位置解析、漏洞规格字段以及差分谓词探测过程。

## 测试与验证

提交前至少运行与改动相关的测试。通用模块可以从以下命令开始：

```bash
PYTHONPATH=src pytest -q src/unit_test
```

漏洞与补丁驱动路线的核心单元测试可以运行：

```bash
PYTHONPATH=src pytest -q \
  src/autoql/tests/test_core.py \
  src/autoql/tests/test_analysis.py \
  src/autoql/tests/test_graph.py \
  src/autoql/tests/test_policy.py
```

涉及外部分析器的改动还应完成相应的集成验证：

- 生成的检查器能够通过目标工具的编译或语法检查；
- 违规测试用例在预期位置产生告警；
- 合规测试用例不产生误报；
- 修复一项问题后，完整测试套件中没有出现新的回归；
- 超时、命令失败和无效模型输出能够被明确记录，而不是被当作成功结果；
- 运行结果中不包含 API Key、本地私有路径或其他敏感信息。

若测试依赖特定版本的 CodeQL、LLVM、PMD 或模型服务，请在 Pull Request 中写明版本。无法在本地执行某项集成测试时，也应说明原因及已经完成的替代验证。

## 代码与文档约定

- 优先复用现有配置和抽象，避免新增硬编码的绝对路径；
- 外部命令必须设置超时，并保留足以诊断失败的标准输出和错误输出；
- 不要吞掉异常或把失败结果记录为成功；
- 新增配置项时提供默认值、用途说明和示例；
- 新增公开函数或复杂逻辑时补充简洁的 docstring；
- 用户可见的工具名称统一写作 `AutoChecker`、`Clang-Tidy`、`Clang Static Analyzer`、`CodeQL`、`PMD` 和 `Semgrep`；
- 中文文档统一使用“规范与测试用例驱动的检查器生成”和“漏洞与补丁驱动的检查器生成”；
- 不提交生成结果、模型缓存、大型临时数据库、构建目录或包含密钥的配置文件。

## Pull Request 检查清单

提交 Pull Request 前，请确认：

- [ ] 改动解决了一个明确的问题，并且没有混入无关修改；
- [ ] 新功能包含合规与违规测试用例，或提供了等价的可复现验证；
- [ ] 相关单元测试和集成测试已经执行；
- [ ] README、部署说明、配置示例和支持矩阵已同步更新；
- [ ] 新增依赖说明了用途，并固定了必要的版本范围；
- [ ] 日志、测试数据和提交内容不包含密钥或敏感信息；
- [ ] Pull Request 描述包含验证环境、命令、结果和已知限制。

## 报告问题

提交 Issue 时，请尽量提供以下信息：

- 使用的生成路线、目标静态分析工具和编程语言；
- AutoChecker、Python 和目标工具版本；
- 最小规则描述、测试用例或可公开的漏洞任务；
- 执行命令、期望结果和实际结果；
- 脱敏后的错误日志和生成结果路径；
- 问题是否可以稳定复现。

请勿在公开 Issue 中粘贴 API Key、未公开漏洞细节或私有源代码。
