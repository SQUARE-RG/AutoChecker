## 最佳实践

### 案例一：从 GJB 8114 编码规范自动生成 Clang-Tidy 检查器

**如何将一份 PDF 编码规范，转化为能够自动发现代码违规问题的静态检查器？**

本案例以《GJB 8114—2013 C/C++ 语言编程安全子集》为例，演示如何使用 AutoChecker，将自然语言编码规范转化为结构化检测规则、自动生成合规与违规测试用例，并最终生成经过编译和测试验证的 **Clang-Tidy 检查器**。

整个过程无需手动为每条规则编写 Clang-Tidy 检查器，实现从**规范文档 → 检测规则 → 测试用例 → 可执行检查器**的自动化转换。

#### 整体流程

```text
                   GJB-8114-2013.pdf
                           │
                           ▼
                 ① PDF 文档解析
                 PaddleOCR PP-StructureV3
                           │
                           ▼
                 document.md + blocks.json
                           │
                           ▼
                 ② 结构化规则提取
                 LLM 分块抽取、合并、去重
                           │
                           ▼
                   autochecker_rules.json
                           │
                           ▼
                 ③ 正反测试用例生成
                 LLM 生成 + C++17 编译验证
                           │
                           ▼
              test_cases/ + rules_with_tests.json
                           │
                           ▼
                 ④ 规则筛选与输入适配
                 检查测试完整性、统一命名
                           │
                           ▼
                  supported_rules.json
                           │
                           ▼
                 ⑤ AutoChecker 检查器生成
                 知识检索 → 代码生成
                    → 编译 → 测试 → 迭代修复
                           │
                           ▼
                 Clang-Tidy 检查器
                 + 测试结果 + 生成报告
```

整个流程分为五个步骤。前三步完成规范解析与测试数据准备，第四步构建 AutoChecker 所需的输入，第五步由 AutoChecker 自动生成并验证检查器。

---

#### Step 1：解析 PDF 规范文档

**目标：将 PDF 中的自然语言规则转化为便于大模型理解和处理的结构化文档。**

本案例使用 PaddleOCR PP-StructureV3 解析 PDF，提取标题、正文、代码示例和表格，同时保留页码及文档层级信息，便于后续追溯规则来源。

**1. 准备解析环境**

首先按照 [PaddleOCR PP-StructureV3 CPU 服务部署指南](doc/paddleocr_service_deployment_cn.md) 安装并启动本地文档解析服务。

**2. 执行 PDF 解析**

```bash
python scripts/parse_regulation_document.py \
  --input doc/GJB-8114-2013.pdf \
  --output-dir result_input_processing/gjb8114-2013
```

默认每 10 页处理一个批次，并保存解析检查点。若解析过程中断，可重新执行命令，从已有检查点继续处理。

**3. 查看解析结果**

```text
result_input_processing/gjb8114-2013/
├── source/
│   └── GJB-8114-2013.pdf       # 原始规范副本
├── paddleocr/
│   ├── batches/                # 分批解析检查点
│   └── raw_response.json       # OCR 原始响应信息
├── document.md                 # 按阅读顺序整理的 Markdown
├── blocks.json                 # 标题、正文、代码等结构块
└── manifest.json               # 文件与解析元数据
```

其中，`document.md` 保存适合 LLM 理解的规范内容，例如：

```markdown
<!-- page: 5 -->

##### 5.1.1.1 准则R-1-1-1

禁止通过宏定义改变关键字和基本类型含义。
```

`blocks.json` 则保存更精细的结构化信息：

```json
{
  "block_id": "page-5-block-12",
  "page": 5,
  "type": "paragraph_title",
  "text": "5.1.1.1 准则R-1-1-1",
  "bbox": [102, 140, 712, 181],
  "confidence": 0.98
}
```

**本阶段产物：** `document.md` 和 `blocks.json`，为后续规则提取提供结构化输入与原文溯源信息。

#### Step 2：自动提取结构化检测规则

**目标：将规范文档中的自然语言条款转化为 AutoChecker 能够理解的结构化规则。**

AutoChecker 的规则提取脚本使用 LLM 分析规范内容，自动识别规则编号、检测要求、规则类型及原文示例，并对跨页或重复抽取的规则进行合并去重。

**1. 执行规则提取**

```bash
python scripts/extract_regulation_rules.py \
  --parsed-dir result_input_processing/gjb8114-2013 \
  --category ucassaat \
  2>&1 | tee result_input_processing/gjb8114-2013/phase2.log
```

**2. 查看提取结果**

本案例的处理结果如下：

| 指标 | 数量 |
| --- | ---: |
| 文档分块（Chunk） | 7 |
| 初始候选规则 | 290 |
| 合并去重后规则 | 204 |
| 强制规则 | 152 |
| 建议规则 | 52 |

主要输出文件包括：

```text
result_input_processing/gjb8114-2013/
├── chunks/                    # 文档分块及来源映射
├── extractions/               # 每个分块的 LLM 提取结果
├── candidates.json            # 合并前的候选规则
├── autochecker_rules.json     # 最终结构化规则
└── phase2.log                 # 执行日志
```

**3. 结构化规则示例**

`autochecker_rules.json` 采用 AutoChecker 的规则数据格式，例如：

```json
{
  "data": {
    "ucassaat": [
      {
        "rule_id": "R-1-1-2",
        "main_title": "no-macro-alias-to-keyword-basic-type",
        "description": "禁止将其他标识宏定义为关键字和基本类型。",
        "rule_type": "required",
        "source_chunks": ["chunk-0001"],
        "examples": [
          {
            "type": "violation",
            "code": "#define JUDGE if\n#define int64 long"
          },
          {
            "type": "compliant",
            "code": "#define JUDGE_ZERO(i) if (0 == (i))\ntypedef long int64;"
          }
        ],
        "rule_test_path": ""
      }
    ]
  }
}
```

关键字段说明：

| 字段 | 作用 |
| --- | --- |
| `rule_id` | 规范中的规则编号 |
| `main_title` | 规则的唯一标识名称 |
| `description` | 需要检查的具体编码要求 |
| `rule_type` | 规则类型，如强制规则或建议规则 |
| `source_chunks` | 规则来源，用于追溯原始文档 |
| `examples` | 从规范中提取的合规与违规示例 |
| `rule_test_path` | 测试用例目录，在下一阶段生成并回填 |

**本阶段产物：** `autochecker_rules.json`，完成从自然语言规范到结构化检测规则的转换。

> **断点续跑：** 每个 Chunk 的提取结果会独立保存至 `extractions/`。重复运行时，已完成的 Chunk 无需重新调用 LLM。

#### Step 3：自动生成正反测试用例

**目标：为每条规则生成能够验证检查器行为的测试套件。**

仅有自然语言描述还不足以准确约束检测逻辑。AutoChecker 进一步为规则生成正反测试用例，用具体代码明确哪些行为应触发告警、哪些行为应被允许。

每条支持的规则默认生成：

- **10 个 Negative Cases（违规用例）**：包含需要检查器识别的违规代码。
- **10 个 Positive Cases（合规用例）**：包含符合规范、不应产生告警的代码。

所有生成的测试文件均通过 C++17 编译器进行基础语法检查。对于编译失败的用例，系统会根据编译器反馈尝试自动修复。

**1. 执行测试用例生成**

在 AutoChecker 项目根目录执行：

```bash
python scripts/generate_rule_tests.py \
  --rules result_input_processing/gjb8114-2013/autochecker_rules.json \
  --output-dir experiment/gjb8114-all/test_cases \
  --output-rules experiment/gjb8114-all/gjb8114_rules_with_tests.json \
  --language cpp \
  2>&1 | tee result_input_processing/gjb8114-2013/phase3.log
```

**2. 查看生成的测试用例**

以规则 `R-1-1-3` 为例：

> 禁止在内层作用域重新定义已有的 typedef 名称。

Negative Case（违规代码）：

```cpp
typedef int mytype;

int main() {
    typedef float mytype; // CHECK-MESSAGES: :[[@LINE]]:{{[0-9]+}}: warning: {{.*}} [ucassaat-r-1-1-3]
    mytype value = 1.0f;
    (void)value;
    return 0;
}
```

该示例在内层作用域中重新定义了 `mytype`，违反规则要求。

其中，`CHECK-MESSAGES` 标记了预期告警位置和 Checker 名称，用于后续验证生成的 Clang-Tidy 检查器是否正确识别违规行为。

Positive Case（合规代码）：

```cpp
typedef int mytype;

int main() {
    mytype value = 1;
    return value;
}
```

该示例符合规则要求，生成的检查器不应报告违规。

**3. 查看测试套件及生成报告**

```text
experiment/gjb8114-all/
├── test_cases/
│   ├── .checkpoints/               # 规则级生成检查点
│   ├── generation_report.json      # 用例生成报告
│   ├── no-typedef-redefinition/
│   │   ├── negative_01.cpp
│   │   ├── ...
│   │   ├── negative_10.cpp
│   │   ├── positive_01.cpp
│   │   ├── ...
│   │   └── positive_10.cpp
│   └── ...
└── gjb8114_rules_with_tests.json   # 回填测试路径的规则
```

测试生成成功后，原始规则将自动补充测试路径和用例数量：

```json
{
  "rule_id": "R-1-1-3",
  "main_title": "no-typedef-redefinition",
  "description": "禁止在内层作用域重新定义已有的 typedef 名称。",
  "rule_type": "required",
  "rule_test_path": "/root/code_check/experiment/gjb8114-all/test_cases/no-typedef-redefinition",
  "negative_case_amount": 10,
  "positive_case_amount": 10
}
```

**测试生成的有效性约束**

系统不会强行生成无法通过基础编译的测试文件。对于无法使用独立 C++ 文件表达的规则，或违规行为本身会直接触发编译错误的规则，系统将记录不支持原因，而不是生成无效测试。

例如，相关规则可能被标记为 `compile_error_only`，其 `rule_test_path` 保持为空，并在 `generation_report.json` 中记录原因。

> **注意：** 所有 Negative Case 和 Positive Case 均需通过基础编译检查，但通过编译不代表满足编码规范。具体的违规或合规行为将在下一阶段通过生成的 Clang-Tidy 检查器验证。

**本阶段产物：** 正反测试套件 `test_cases/` 和包含测试信息的 `gjb8114_rules_with_tests.json`。

#### Step 4：准备 AutoChecker 检查器生成输入

**目标：从已经生成测试用例的规则中筛选有效规则，整理为 AutoChecker 可直接使用的输入格式。**

并非所有自然语言规则都适合当前的 Clang-Tidy 自动生成流程，因此需要对第三步的结果进行筛选。

主要检查：

1. `rule_test_path` 非空，且对应测试目录存在。
2. 正反测试用例数量完整，文件已通过基础编译。
3. 规则包含 Clang-Tidy 生成入口所要求的 `category` 字段。
4. 测试文件中的 Checker 名称与实际生成名称保持一致。

整理后的输入文件为：

```text
experiment/gjb8114-all/gjb8114_clang_tidy_supported_rules.json
```

示例：

```json
{
  "data": {
    "ucassaat": [
      {
        "rule_id": "R-1-1-3",
        "main_title": "no-typedef-redefinition",
        "description": "禁止在内层作用域重新定义已有的 typedef 名称。",
        "category": "ucassaat",
        "rule_test_path": "/root/code_check/experiment/gjb8114-all/test_cases/no-typedef-redefinition",
        "negative_case_amount": 10,
        "positive_case_amount": 10
      }
    ]
  }
}
```

**特别注意：统一 Checker 命名**

测试生成阶段默认按照 `category-rule_id` 写入测试标记，例如：

```text
[ucassaat-r-1-1-3]
```

而 Clang-Tidy 检查器生成入口使用 `category-main_title` 命名，例如：

```text
[ucassaat-no-typedef-redefinition]
```

因此，在启动 AutoChecker 前，必须统一两者的命名。

可以将测试文件中的标记统一修改为：

```text
[ucassaat-no-typedef-redefinition]
```

也可以将生成 Checker 时使用的名称统一规范化为 `r-1-1-3`。

**测试中的 Checker 名称必须与实际生成名称一致，否则即使检查器正确报告了违规，也可能因为测试标记不匹配而导致验证失败。**

#### Step 5：运行 AutoChecker，生成 Clang-Tidy 检查器

**目标：根据规则描述和正反测试用例，自动生成通过编译及测试验证的 Clang-Tidy 检查器。**

完成 Clang-Tidy 开发环境部署，并配置 `src/config.json` 中的相关路径后，运行：

```bash
python src/main.py \
  --platform clang-tidy \
  --rules experiment/gjb8114-all/gjb8114_clang_tidy_supported_rules.json
```

**AutoChecker 将自动执行完整的检查器开发流程：**

| 阶段 | AutoChecker 执行的操作 |
| --- | --- |
| ① 理解检测需求 | 分析规则描述及正反测试用例，提取关键检测条件 |
| ② 检索分析知识 | 结合 AST、AST Matcher 和静态分析 API 知识，获取实现检查器所需的信息 |
| ③ 生成检查器 | 自动生成 Clang-Tidy Checker 的头文件、实现文件及检测逻辑 |
| ④ 编译验证 | 将候选 Checker 集成至 LLVM/Clang-Tidy 工具链并编译，自动修复编译错误 |
| ⑤ 执行测试 | 运行全部正反测试用例，检查漏报与误报 |
| ⑥ 反馈迭代 | 根据测试失败信息调整检测逻辑，重新编译并回归测试 |
| ⑦ 保存结果 | 输出 Checker 源码、测试报告、运行指标和各轮迭代记录 |

整个流程持续进行，直到满足测试要求或达到预设迭代上限。

**生成的 Checker 示例**

对于前面的 `no-typedef-redefinition` 规则，AutoChecker 会生成相应的 Clang-Tidy Checker。

其核心实现结构类似：

```cpp
void NoTypedefRedefinitionCheck::registerMatchers(
    MatchFinder *Finder) {
  Finder->addMatcher(
      typedefDecl().bind("typedefDecl"), this);
}

void NoTypedefRedefinitionCheck::check(
    const MatchFinder::MatchResult &Result) {

  const auto *Decl =
      Result.Nodes.getNodeAs<TypedefNameDecl>("typedefDecl");

  // 判断当前 typedef 是否遮蔽外层同名声明。
  // 实际检测逻辑由 AutoChecker 自动生成。

  if (Decl /* && 满足违规条件 */) {
    diag(Decl->getLocation(),
         "禁止重新定义已有的 typedef 名称");
  }
}
```

以上仅展示检查器的核心结构，实际的 AST 匹配、作用域分析和违规判定逻辑由 AutoChecker 根据规则及测试反馈生成。

result_generation/clang-tidy/gjb8114_security_rules/

**批量任务中断后如何继续？**

对于较大规模的规则集，AutoChecker 支持继续执行中断任务：

```bash
python src/main.py \
  --platform clang-tidy \
  --rules experiment/gjb8114-all/gjb8114_clang_tidy_supported_rules.json \
  --resume
```

如果需要重新尝试之前生成失败的规则，可使用：

```bash
python src/main.py \
  --platform clang-tidy \
  --rules experiment/gjb8114-all/gjb8114_clang_tidy_supported_rules.json \
  --retry-failed
```

#### 最终成果

通过以上五个步骤，我们将一份原本只能供开发者阅读的 PDF 编码规范，转化为能够在 Clang-Tidy 中执行的自动化检查能力。

| 输入 | 自动化处理 | 最终输出 |
| --- | --- | --- |
| GJB 8114 PDF 规范 | 文档解析与规则提取 | 结构化规则 JSON |
| 自然语言规则 | LLM 生成与编译校验 | 合规、违规测试套件 |
| 检测规则与测试套件 | 知识检索、代码生成、编译验证与反馈修复 | Clang-Tidy 检查器源码及验证报告 |

**这个案例展示了 AutoChecker 的核心价值：开发者无需逐条手动设计 AST Matcher、实现 Checker 类并反复调试，就可以将自然语言编码规范转化为可复用的自动化检查能力。**

生成的检查器可进一步集成到 Clang-Tidy 工具链，应用于实际项目的代码质量检查与持续集成流程。
