# Introduction

软件漏洞是威胁软件系统安全性与可靠性的重要因素。随着软件系统规模与复杂性的不断增长，大量安全漏洞被持续发现并公开披露。以 Common Vulnerabilities and Exposures（CVE）为代表的公开漏洞记录积累了丰富的真实世界漏洞知识，包括漏洞描述、受影响的软件版本以及相关修复补丁。这些信息不仅揭示了特定软件中的安全缺陷，还为发现其他软件系统中具有相同根本原因的潜在漏洞提供了重要依据。然而，修复一个已知漏洞并不意味着其他软件中具有相似缺陷模式的漏洞也得到了消除。因此，如何有效利用已披露的漏洞知识，系统性地发现不同软件系统中的同类漏洞，是软件安全领域的重要研究问题。

静态程序分析为解决这一问题提供了有效的技术手段。以 CodeQL、Clang Static Analyzer 和 PMD 为代表的静态分析工具，通过执行针对特定缺陷模式设计的检查器（Static Analysis Checkers），识别程序中潜在的安全漏洞。与针对单个代码仓库的漏洞分析不同，静态分析检查器能够将漏洞知识转化为显式、可执行且可复用的检测逻辑，并将其应用于不同软件项目及持续集成流程。近年来，基于大语言模型（Large Language Models, LLMs）的智能体也被广泛探索用于自动化漏洞检测。尽管此类方法能够通过动态代码探索与推理识别潜在安全缺陷，但在不同代码仓库中重复检测已知漏洞模式通常仍需要重新执行模型推理。相比之下，**将已知漏洞转化为静态分析检查器，能够把一次性的漏洞分析结果固化为可重复执行的检测能力**，减少后续检测对模型推理的依赖，并提高检测逻辑的可审查性与可复用性。因此，从已知漏洞中自动构建静态分析检查器，为规模化、持续化地发现同类漏洞提供了一条具有重要应用价值的技术路径。

然而，静态分析检查器的开发高度依赖安全分析与程序分析领域的专业知识。开发者不仅需要深入理解漏洞的根本原因，分析漏洞代码及其修复补丁，提取漏洞成立所需的关键语义条件，还需要将这些条件转化为具体静态分析框架所支持的检测逻辑，并借助抽象语法树、控制流和数据流等程序分析信息实现检查器。此外，为了发现不同软件系统中的同类漏洞，检查器还需要在检测准确性与泛化能力之间取得平衡，避免过度依赖特定项目的实现细节。复杂的漏洞分析、检测逻辑设计与实现过程，使人工开发检查器具有较高的时间成本和技术门槛，难以满足不断增长的漏洞检测需求。

近年来，大语言模型在程序理解与代码生成方面展现出的能力，为自动化静态分析检查器合成（Static Analysis Checker Synthesis）提供了新的可能性。已有研究，如 QLCoder、KNighter 和 AutoChecker，探索了利用 LLM 自动生成静态分析检查器的方法。这些方法普遍采用**迭代式生成与验证（Iterative Generation and Validation）**框架：首先根据漏洞描述、修复补丁或测试用例生成候选检查器，随后通过编译和执行验证其正确性，并利用验证反馈驱动 LLM 不断修复候选检查器，直至满足预期的检测行为。这一框架能够利用外部工具反馈逐步改进生成结果，降低检查器开发对人工专家的依赖。然而，迭代式合成的有效性不仅取决于初始检查器的生成质量，还在很大程度上取决于验证反馈能否为后续修复提供有效指导。

**现有方法在检查器的语义错误修复方面仍面临重要挑战。** 当候选检查器存在语法错误或调用了不存在的分析 API 时，编译器通常能够提供明确的错误位置和诊断信息，使 LLM 可以通过检索相关文档进行针对性修复。相比之下，当一个语法正确的检查器未能检测出目标漏洞时，整体执行结果通常只能表明检测行为不符合预期，却难以揭示错误产生的具体原因。静态分析检查器通常由多个相互关联的检测条件构成，检测失败可能源于错误的语法结构匹配、不准确的 API 识别、缺失的数据流关系，或多个检测条件之间不一致的变量绑定。由于缺乏对内部检测逻辑的细粒度诊断，LLM 往往只能依赖自身推理猜测潜在错误，并通过反复修改和执行检查器验证猜测。这种修复方式不仅可能修改原本正确的检测条件，还可能在多轮迭代中重复进行缺乏依据的尝试。尽管增加迭代次数可能提高部分检查器的修复成功率，但**更多的迭代并不能从根本上弥补诊断信息的缺失**，也无法保证每次修复能够有效缩小错误范围。因此，如何从检查器的实际执行行为中获取可操作的诊断信息，并据此指导语义修复，是提升迭代式检查器合成效率的关键问题。

我们观察到，尽管静态分析检查器的整体检测行为可能十分复杂，但其检测逻辑通常可以分解为一组相互关联的谓词（Predicates），分别描述程序元素的结构特征、语义属性以及元素之间的关系。一个检查器能否成功报告目标漏洞，取决于这些谓词及其关联约束能否在目标程序中共同得到满足。因此，**检查器的语义错误并非完全不可观察，其内部谓词的匹配结果及依赖关系能够为错误定位提供细粒度的执行证据**。例如，当某个谓词无法匹配预期程序元素时，其检测条件可能过于严格或建模不准确；当多个谓词分别能够匹配程序元素，但其联合约束无法成立时，问题则可能存在于谓词间的变量绑定或语义关系中。通过分析这些细粒度的匹配行为，可以逐步缩小潜在错误范围，而不必仅凭检查器的整体执行结果进行猜测。更进一步，不同类型的语义错误通常对应不同的修复需求，使得将诊断结果映射为具有明确修改目标的修复操作成为可能。这一观察为构建由实际执行证据驱动的检查器语义修复机制提供了基础。

基于上述观察，本文提出一种**基于谓词级错误定位与模板引导修复的静态分析检查器合成方法**，旨在提升迭代式检查器合成过程中语义修复的有效性与收敛效率。具体而言，我们首先将候选检查器的检测逻辑表示为谓词依赖图（Predicate Dependency Graph），显式刻画各检测条件及其依赖关系；随后，通过细粒度的谓词执行分析，获取各谓词及其组合在目标程序中的实际匹配情况，并结合依赖关系定位可能导致整体检测失败的语义错误；最后，根据错误类型选择相应的语义修复模板（Semantic Repair Templates），为 LLM Agent 提供具体的执行证据、待修改的检测逻辑以及针对性的修复指导。通过将传统的整体结果反馈转化为细粒度的错误诊断与结构化修复建议，本文旨在减少缺乏依据的修复尝试，使自动化检查器合成过程能够在有限的计算与推理预算下更加有效地收敛。
